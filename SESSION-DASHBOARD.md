# Session Data Website & Database

Website for reviewing Project DELTA collection sessions and the readings
recorded during them. Everything on the page is read from PostgreSQL
(Neon) by `server/server.js` — no numbers are generated by the page.

---

## 0. AI agent quick start — set up the WHOLE DELTA folder

An AI agent (OpenCode, Cursor, Copilot…) can install and run this whole
project on a Raspberry Pi. Give it this prompt:

> Read `SESSION-DASHBOARD.md` and `README.md` in this repo. Set up the whole
> Project DELTA folder on this Raspberry Pi: server, kiosk, session website.
> Ask me for the DATABASE_URL before writing `server/.env`. Run every command
> yourself and report each result.

## 1. How a session becomes data

```text
OPERATOR presses START MONITORING (kiosk, index.html)
   └─ POST /api/sessions          → detection_sessions row (client_key = web-<uuid>)

Camera reader ─┐
               ├─ POST /api/measurements  → measurements row
Any other source ┘        (studentCode + source + metrics)
                                          │
                                          └─ server stores the running session's
                                             key in session_client_key

OPERATOR session ends (after 15 s) → POST /api/sessions/end → detection_sessions.ended_at

WEBSITE (sessions.html)
   └─ GET /api/stats
   └─ GET /api/sessions                 history + record counts
   └─ GET /api/sessions/:key/records    the readings of one session
   └─ GET /api/sessions/:key/export.csv CSV for the data collection sheet
```

The Raspberry Pi sensor services were **not modified**. They post exactly as
before; the server attaches each reading to the student's currently running
session (`api/_lib.js` → `resolveOpenSessionKey`). Any source that can reach
`POST /api/measurements` is stored the same way.

### Readings recorded before a session exists

A reading belongs to a session when `measurements.session_client_key` equals
the session key. Readings posted outside any monitoring session (the sensors
run continuously) stay `NULL` and are shown as *unassigned*.

Readings stored **before** this linking existed are matched by time window:
`recorded_at` between the session start and end. The website shows them with
`session_match = time_window` in the table and in the CSV, so the origin of
every row is visible. The same rule is used by `wireless-report/report-server.js`.

## 3. Install and initialise

On the Raspberry Pi (or any machine on the same network):

```bash
cd ~/DELTA/server
npm install                     # installs pg (already in package.json)
cp .env.example .env            # then set DATABASE_URL and PORT
npm run setup-db                # applies server/schema.sql (idempotent)
```

`server/.env` (git-ignored, never commit it):

```ini
DATABASE_URL=postgresql://USER:PASSWORD@HOST/DBNAME?sslmode=require
PORT=8000
```

`npm run setup-db` only creates what is missing and adds one index
(`idx_measurements_session`). It never drops or rewrites collected data.

## 4. Start, stop, restart

```bash
cd ~/DELTA/server
npm start                 # kiosk + API + session website on port 8000

sudo systemctl restart delta-server    # when installed as a service
sudo systemctl stop delta-server       # stop
sudo systemctl status delta-server     # check
sudo journalctl -u delta-server -n 50  # read the log
```

The system services created by `_pi-setup/raspberry-pi/install-services.sh`
(`delta-server`, `delta-kiosk`, `delta-camera`) need no changes — the
website is served by `delta-server` on the same port.

| URL | Purpose |
|---|---|
| `http://localhost:8000/` | kiosk terminal (unchanged) |
| `http://localhost:8000/sessions.html` | **session data website** |

From another device on the same LAN, replace `localhost` with the Pi's
address, e.g. `http://192.168.1.50:8000/sessions.html`
(find it with `hostname -I`). The kiosk carries a small **SESSIONS** link in
its header that opens the website.

## 5. What the website shows

* **Overview** — total sessions, total readings, how many readings carry a
  session key, how many sessions are active, the latest session and the
  recording date range. Every number is a `COUNT` from PostgreSQL.
* **Session history** — session id, student, start, end, duration, number of
  records and status (`ACTIVE`, `COMPLETED`, `INTERRUPTED`), searchable by
  session id or student and filterable by date and status, with paging.
* **Session detail** — session facts, per-metric min/avg/max over the whole
  filtered set, and the readings in a scrollable table. Missing values show
  as `—`; a stored `0` shows as `0`.
* **Filters** — session id/student search, date range, status, rows per page;
  in the detail view also source, date range, sort column and direction.
* **CSV export** — one session, or every reading.

## 6. CSV export (data collection sheet)

* Per session: **CSV** button in the session row, or **EXPORT THIS SESSION
  (CSV)** inside the detail view. Only that session's readings are exported.
* Everything: **EXPORT ALL RECORDS (CSV)** above the history table; it
  honours the date range currently set in the history filters.

Properties:

* header row with `snake_case` column names;
* `recorded_at_utc` is ISO 8601 UTC (`2026-10-13T14:00:04.076Z`);
* `session_id` holds the stored key (empty when the reading was matched by
  time window) and `session_match` states how the row was associated;
* values are written exactly as stored — a missing value is an empty cell,
  never `0`;
* commas, quotes, CR and LF are escaped per RFC 4180;
* a UTF-8 BOM is included so spreadsheet apps open it correctly;
* at most 100 000 rows per export.

Files are named e.g. `delta-session-web-ffe68e0a-…-2026-10-16-07-05-24.csv`.

## 7. API added

All read-only, all parameters validated and bound.

| Method & path | Purpose |
|---|---|
| `GET /api/stats` | overview counters |
| `GET /api/sessions?limit=&page=&q=&from=&to=&status=&order=` | session history |
| `GET /api/sessions/:key/records?limit=&page=&source=&from=&to=&sort=&order=` | readings of one session |
| `GET /api/sessions/:key/export.csv` | CSV (`:key` = session id, `all`, or `unassigned`) |

`:key` accepts a session id, `all` (every reading) or `unassigned` (readings
without a session). Invalid input answers `400` with a message; an unknown
session answers `404`.

## 9. Backing up the collected data

The data lives in the Neon PostgreSQL database. From the repository root:

```bash
# whole database (structure + data) as a custom-format dump
pg_dump "$DATABASE_URL" -Fc -f delta-$(date +%F).dump

# restore into an empty database
pg_restore -d "$NEW_DATABASE_URL" -Fc delta-2026-10-16.dump

# or plain SQL for inspection
pg_dump "$DATABASE_URL" --data-only -t measurements -t detection_sessions \
  -f delta-records-$(date +%F).sql
```

Check counts at any time:

```bash
cd ~/DELTA/server && npm run setup-db      # prints the tables
node -e "require('./check-db.js')"         # prints sessions / measurements counts
```

## 10. Optional: link historical readings (dry run first)

Readings collected before session linking have no session key. They are
already shown in the website through the session time window, so this step
is optional — it only makes the stored `session_client_key` column explicit.

```bash
cd ~/DELTA/server
node link-historical-sessions.js --explain 10   # dry run, writes nothing
node link-historical-sessions.js               # dry run summary
node link-historical-sessions.js --apply       # writes session_client_key
```

Only readings that fall inside **exactly one** session window are written;
ambiguous readings are counted and left untouched. Nothing is deleted.

## 11. Access and security

* Intended for the local network only. The server binds the same interface
  it already used for the kiosk — do **not** forward port 8000 to the
  internet, and do not put it behind a public reverse proxy without adding
  authentication.
* There is no login on the session pages; the data is health data. Restrict
  access at the network level (private Wi-Fi / VLAN, or SSH tunnel:
  `ssh -L 8000:localhost:8000 user@pi-ip`).
* `DATABASE_URL` lives only in `server/.env`, is read by the server process
  and is never sent to the browser. No credentials appear in `sessions.html`,
  `sessions.js` or `sessions.css`.
* Every query the website issues is a parameterised `SELECT`. The website
  exposes no delete or update endpoint.

## 12. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `DATABASE_URL missing` | `server/.env` missing — copy `server/.env.example`, set the value |
| Website shows "DATABASE OFFLINE" | database unreachable; `curl http://localhost:8000/api/health` must return `{"ok":true,...}`; check credentials and network |
| Session list is empty | no session has been started yet; run one from the kiosk |
| A session shows 0 records | no reading fell inside it — normal for interrupted sessions |
| Reading count does not rise | the sensor services are not posting: `systemctl status delta-camera`, `journalctl -u delta-camera -n 30` |
| `column ... does not exist` in the log | run `npm run setup-db` to apply the additive migration |
| Port 8000 already in use | stop the other process or set `PORT` in `server/.env` |
| CSV opens with odd characters in Excel | file already carries a UTF-8 BOM; import as UTF-8 if the app overrides it |
